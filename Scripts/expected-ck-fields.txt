# Every CloudKit field the app can EVER write across all synced record types — the
# source of truth for the release-time Production-schema check (verify-prod-schema.sh)
# and the CKFieldCoverageTests unit test (which derives this list from the live
# SwiftData models, so drift between the models and this file fails `swift test`).
#
# Record types the container mirrors: CD_NoteEntity (notes ground truth) plus the
# agent layer — CD_TagEntity, CD_MemoryEntity, CD_ViewRevisionEntity,
# CD_InstructionsEntity, CD_InteractionStateEntity. Field names below are the flat
# union across those types (CloudKit prefixes stored fields CD_<name>; shared names
# like CD_id / CD_createdAt / CD_agentId / CD_viewName / CD_updatedAt recur across
# types and are listed once). verify-prod-schema.sh greps each name against the
# exported Production schema. 31 field names → verify-prod-schema.sh expects 31/31.
#
# RULES (learned from two production outages — see docs/cloudkit-sync-troubleshooting.md):
#  - every stored attribute `x` on any synced model appears here as CD_x
#  - every Data-typed attribute ALSO needs its lazily-materialized CKAsset twin
#    CD_x_ckAsset (CoreData+CloudKit switches from inline bytes to an Asset when a
#    value crosses the size threshold — Development auto-creates the field at that
#    moment; Production REJECTS it and the whole export batch wedges, silently)
#  - after editing this file: add the field(s) in the CloudKit Dashboard's
#    Development schema, then Deploy Schema Changes to Production
